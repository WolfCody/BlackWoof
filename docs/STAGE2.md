## 2. Реализовано в Stage 2

- Rust audio engine с отдельным потоком воспроизведения трека.
- Декодирование через Symphonia `0.6.0`.
- Конфигурация декодеров для MP3, FLAC, WAV/PCM и OGG Vorbis.
- Mono и stereo; частота дискретизации 8–192 kHz.
- Вывод PCM через прямой AAudio FFI.
- JNI-мост между Android Java API и Rust; 7 JNI exports.
- Передача открытого файла через FD с передачей владения Rust.
- Команды Play, Pause, Resume, Stop и получение состояния.
- Обработка ошибок и защита JNI-границ от распространения Rust panic.
- Пропуск изображений обложек в настройках чтения метаданных.
- Временный ZERO-FRILLS тестовый экран для выбора одного файла и управления тестовым воспроизведением.

Форматы в Cargo feature set и тестовых фикстурах не следует путать с гарантией поддержки любого файла с соответствующим расширением: фактический результат зависит от корректности файла и возможностей включённого декодера.

## 3. Что ещё не реализовано

Это не функции Stage 2 и не должны описываться как готовые:

- внутренняя музыкальная библиотека / MediaStore browser;
- очередь треков, Previous / Next;
- Shuffle и Repeat;
- seek и отображение позиции;
- сохранение и восстановление последнего трека/позиции;
- Foreground Service;
- MediaSession и системное медианотификейшен;
- аудиофокус и полноценная координация с другими аудиоприложениями;
- подтверждённое фоновое воспроизведение;
- финальный пользовательский интерфейс.

`MainActivity` — временный тестовый стенд, а не финальный UI. Сейчас он использует `ACTION_OPEN_DOCUMENT` с MIME type `*/*` для выбора отдельного файла. Это не внутренняя библиотека и не MediaStore-каталог.

## 5. Зависимости и политика логирования

Прямые зависимости:

| Crate | Назначение |
|---|---|
| `symphonia =0.6.0`, `default-features = false`, features `flac mp3 ogg pcm vorbis wav id3v1 id3v2` | Декодирование включённых аудиоформатов |
| `log 0.4` с feature `max_level_off` | Не используется как логгер приложения; нужен транзитивному дереву Symphonia и компилирует вызовы log-макросов на уровне Off |

Реальные реализации логирования и сетевые crates запрещены CI policy. Проверка `scripts/check_log_facade.py` требует ровно одну разрешённую версию `log` с `max_level_off`. Верификатор APK также проверяет отсутствие Android logging API / `liblog`.

## 6. Архитектурные решения

1. Один поток воспроизведения на трек (`bw-audio`): декодирование → блокирующая запись в AAudio. На паузе поток ожидает через condition variable.
2. Вывод: AAudio, shared, `POWER_SAVING`, i16, usage MEDIA, content MUSIC.
3. Порция — 4096 кадров (`CHUNK_FRAMES`); настройка размера отложена до измерений.
4. Формат потока определяется декодером до открытия аудиовыхода.
5. Обложки не нужны; `limit_visual_bytes = Limit::Maximum(1)` ограничивает чтение визуальных метаданных.
6. Повреждённые пакеты могут пропускаться в пределах заданного лимита; mono/stereo поддерживаются, более двух каналов отклоняются.
7. FD передаётся в Rust с передачей владения; закрытие выполняется владельцем файла ровно один раз.
8. JNI-функции и поток воспроизведения защищены `catch_unwind`; panic hook не выводит диагностические сообщения.
9. Ошибки представлены `ErrorKind` без текстовой истории.
10. При ошибках вывода предусмотрены ограниченные повторные открытия sink.

## 7. Решения владельца и постоянное состояние

Зафиксированные проектные решения:

- Package: `com.dzekiwolf.blackwoof`.
- Symphonia `0.6.0`; `log` допускается только с `max_level_off`.
- Целевая философия: Rust-first, offline-first, ZERO-FRILLS.
- Только mono/stereo; многоканальный звук пока не входит в объём.
- Обложки не загружаются и не хранятся.

Ранее согласованное намерение хранить только последнее воспроизведение не означает, что persistence уже реализована: сохранение и восстановление трека/позиции отсутствуют в текущем Stage 2.

## 8. Android manifest и SDK

`android/AndroidManifest.xml` содержит launcher activity и не объявляет `uses-permission`. В частности, `INTERNET` отсутствует. Уровни SDK задаются при сборке через `aapt2` в `scripts/build_apk.sh`: `minSdk 28`, `targetSdk 35`.

Foreground Service, MediaSession и разрешения для фонового воспроизведения пока не добавлены.

## 9. Cargo.lock, CI и подпись

- `Cargo.lock` присутствует в корне репозитория и закоммичен в `main` коммитом `5305959` (`Add Cargo lockfile`).
- Workflow проверяет наличие lockfile и использует `--locked` для последующих Cargo-команд.
- Не пересоздавать и не редактировать lockfile вручную. Изменения зависимостей должны быть отдельными, намеренными и проверяемыми.
- Временный signing key создаётся в `RUNNER_TEMP` вне репозитория и удаляется `EXIT` trap при успехе или ошибке.
- Пароль передаётся через окружение и не печатается. Ключ не включается в артефакты.
- Артефакт CI `blackwoof-stage2` содержит APK и диагностические отчёты сборки/проверок.

## 10. Повторная проверка и дальнейшие действия

Для повторного CI-запуска: GitHub → Actions → workflow `ci` → выбрать запуск. Артефакт успешного запуска доступен в разделе Artifacts.

Для проверки на устройстве владелец может установить APK из артефакта. Так как без постоянного signing key подпись может отличаться между сборками, обновление поверх предыдущей установки может потребовать удалить старую сборку.

Текущий документ фиксирует только подтверждённые результаты Stage 2. Дополнительные проверки длительного воспроизведения, переключения аудиоустройств, Bluetooth, всех повреждённых файлов и фонового режима не заявляются как пройденные на физическом устройстве.
